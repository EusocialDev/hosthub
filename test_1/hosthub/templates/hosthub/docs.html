How HostHub, Bland, and restaurant operations connect.

This page explains the API calls and workflows around HostHub so new contributors can understand what happens during a Bland conversation, after a call ends, and inside the restaurant dashboard.

System Overview

HostHub is a Django dashboard for restaurant teams using Bland.ai voice agents. Bland handles the guest conversation. HostHub stores the outcome, routes the call to the right restaurant/location, and gives staff a workflow for review, follow-up, live monitoring, transfer, reports, and operations.

During the call

Bland may call public HostHub endpoints for real-time context, such as restaurant hours.

After the call

Bland posts final call data to HostHub, where the call is categorized and tenant-routed.

Inside HostHub

Staff see only calls for their authorized account and locations.

External actions

HostHub can trigger GHL reservation messages, carryout recovery SMS, and daily reports.

Tenant Model

HostHub is multi-tenant by restaurant account and location. The operational routing key is the phone number the guest dialed. 

Account
  Location
    PhoneNumber
      Call

When a final Bland call arrives, HostHub normalizes the Bland to number and matches it to an active PhoneNumber. That match assigns the call to the correct Account and Location.

Tenant safety rule If a final call cannot be matched to an active phone number, it should not appear in any dashboard.

During-Call Bland API Calls

These are API calls Bland can make while the guest is still on the phone. They are different from final webhooks because the AI may use the response immediately to decide what to say or do next.

GET /test/api/hours/<location_slug>/ public used by Bland

Returns regular hours, special date overrides, and timezone for one active location. Bland can call this during a conversation when it needs current restaurant-hours context.

When Bland should call it

  • When a caller asks if the restaurant is open today.
  • When a caller asks about hours for a specific day.
  • When a pathway needs date overrides before answering holiday or closure questions.
  • When the AI needs location-specific hours instead of hardcoded pathway text.

Response shape

{
  "location": "160 Main",
  "timezone": "America/Detroit",
  "regular_hours": {
    "monday": {"closed": false, "open": "11:00", "close": "21:00"},
    "tuesday": {"closed": false, "open": "11:00", "close": "21:00"},
    "sunday": {"closed": true}
  },
  "date_overrides": [
    {
      "name": "Christmas Day",
      "start_date": "2026-12-25",
      "end_date": "2026-12-25",
      "closed": true
    }
  ]
}

Bland configuration notes

  • Use the location slug that belongs to the restaurant/location pathway.
  • Do not hardcode secrets in this call. This endpoint is public by design.
  • If Bland stores the location slug in a variable, keep that variable synchronized with the HostHub Location.slug.
  • A wrong or inactive slug returns a not-found response and Bland should fall back gracefully.
Where to document additional Bland tool calls If a Bland pathway calls another HostHub endpoint during the conversation, add it to this section with the method, path, purpose, required pathway variables, request payload, response shape, and fallback behavior.

Post-Call Ingestion

After a call ends, Bland sends the final payload to HostHub. This is where the system creates the dashboard call record, stores transcripts, maps categories, and triggers post-call automation.

POST /test/webhooks/bland/calls/<token>/ Bland webhook

Receives both live transcript events and final call payloads. The URL token must match BLAND_WEBHOOK_TOKEN.

Routing logic

if "message" in payload and payload.get("category") == "call":
    ingest_bland_webhook_event(payload)
else:
    upsert_call_from_bland_json(payload)

Final payload behavior

  1. Read call_id or c_id.
  2. Ignore very short calls under 16 seconds.
  3. Map pathway_tags into display_category.
  4. Match Bland to number to an active PhoneNumber.
  5. Upsert the Call by bland_call_id.
  6. For carryout calls, optionally trigger cart recovery SMS.
POST live transcript event to Bland webhook streaming transcript

Live transcript events create or update CallSession and TranscriptTurn rows. They are used by the live-call transcript panel.

Recognized message prefixes:

  • Agent speech: or Agent says: maps to agent text.
  • Handling user speech: or User speech: maps to user text.

Dashboard APIs

These endpoints are used by the HostHub dashboard after a worker logs in. They are scoped to the logged-in user's account and authorized locations unless noted otherwise.

Method Path Purpose
GET /api/bland/live-calls/ Poll active Bland calls and filter them to authorized phone numbers.
POST /api/bland/transfer-call/ Transfer an active Bland call to the location transfer target.
GET /test/api/calls/<call_id>/turns/ Load live transcript history for a call session.
GET /test/sse/call/<call_id>/ Stream live transcript updates with SSE.
GET /test/transcript/call/<call_id>/ Load final transcript JSON for a stored call.
POST /calls/<call_id>/mark-handled/ Mark a call resolved or move it back to needs action.
POST /calls/<call_id>/confirm-reservation/ Send reservation confirmation through GHL and resolve the call.
GET /api/new-calls-boolean/ Show the dashboard refresh pill when new calls were ingested after page load.

External Side Effects

Some workflows create external effects. These are the parts that operators and developers need to understand before changing pathway variables, payload shapes, or timing.

Reservation confirmation through GHL

Triggered from the dashboard when staff clicks the reservation confirmation button. HostHub sends a payload to GHL_RESERVATION_CONFIRMATION_WEBHOOK_URL. On success, the call is resolved with disposition reservation_confirmed. 

{
  "call_id": 123,
  "guest_name": "Guest",
  "guest_phone": "+15555550123",
  "reservation_date": "2026-08-25",
  "reservation_time": "7:00 PM",
  "reservation_guests": "4",
  "restaurant_name": "Restaurant"
}

Carryout cart recovery SMS

Triggered after final carryout ingestion when there is an order_cart, the kitchen did not print, and no recovery SMS was already sent. HostHub creates a cart import link, then posts to RECOVERY_SMS_WEBHOOK_URL.

Skip conditions:

  • The call is not categorized as carryout.
  • recovery_sms_sent_at is already set.
  • variables.kitchen_print is true.
  • No valid cart items exist.
  • The caller phone number cannot be normalized.

Daily reports through Resend

The send_daily_call_report management command builds account-scoped call summaries and sends email through Resend for accounts with reporting enabled.

Categories And Bland Variables

HostHub display categories come from Bland pathway_tags. The selected category controls dashboard filters, detail panel fields, and available resolution dispositions.

Category Tag rule Common variables shown in HostHub
reservation Tag contains reservation user_name, guest, date, time, request, user_message
carryout Tag contains carryout order_summary, total_price, order_cart, kitchen_print, user_message
leave_message Tag contains leave user_message
private_events Tag contains private occasion, party_date, party_time, guests, party_message, user_message
other No known tag match summary, transcript, metadata
Change rule If a Bland variable name changes, update the dashboard template data-* attributes and the JavaScript detail rendering together.

Hours And Pathway State

Location hours are used in two ways: during the conversation for guest-facing answers, and outside the conversation to control Bland's inbound open/closed pathway.

Guest-facing hours

Bland should use /test/api/hours/<location_slug>/ to fetch regular hours and date overrides before answering time-sensitive hours questions.

Inbound pathway state

The staff area and schedule processor can sync Location.expected_pathway_id to Bland's inbound phone-number configuration. Open and closed states use separate pathway IDs on the location. 

POST https://api.bland.ai/v1/inbound/<phone_number>

{
  "pathway_id": "expected_open_or_closed_pathway_id"
}

Adding New API Calls

When adding a new HostHub or Bland integration, document it here at the same time as the code or pathway change.

For a new during-call Bland call

  • Document the exact method and path.
  • State why Bland calls it during the conversation.
  • List required Bland pathway variables.
  • Show the request payload and response shape.
  • Explain fallback behavior if the endpoint fails.
  • Confirm whether the endpoint is public, token-protected, or dashboard-authenticated.

For a new post-call side effect

  • State what triggers it and what prevents duplicates.
  • List external service, env vars, and payload fields without exposing secret values.
  • Describe the call state changes after success or failure.
